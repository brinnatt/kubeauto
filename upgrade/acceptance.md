# 升级验收与证据复用

## 1. 已交付基线与本次新增主张

交付负责人已确认：`v1.33.6` 的全部功能、组件、中间件及存储已经 GA，生产稳定。
本次从该事实出发维护版本，不重开旧 GA。需要关联的客户 tag、制品、配置和
证据身份，只用于判断某份证据能否支持目标主张；缺口不等于旧产品未 GA。

目标 `test-matrix.yaml` 是本次升级的验收主线；原矩阵保留原 ID、状态和结论。
`acceptance-plan.yaml` 连接官方约束、旧证据和变化补证，不另计一套 PASS。
验收覆盖完整，证据取得方式可以不同；覆盖一项能力不等于本轮重跑该能力。
15 个父项是结论归属，不是 15 次独立建群或全量回归任务。

本轮是方案阶段，正式升级项均保持 `pending`，没有专用 validator/runner/status
命令。本地检查、证据复制不签目标 PASS。后续实现准入与汇报沿用根 AGENTS；
有真实现场动作的子项才要求对应运行命令、marker、租约和清理。资料核对、
归档校验、静态合同使用各自适当的检查方式，不为填矩阵字段强造现场动作。

## 2. 证据实际归档与适用性分开判断

源版正式证据和矩阵快照复制到 `v1.33.6/evidence/`，来源及逐文件 SHA256、
字节数、原矩阵 ID 记入 `v1.33.6/evidence-manifest.yaml`。原文件保持不动，副本
逐字节保留内容及历史状态，不改日期、输入 hash、失败记录或原签署范围。
目标计划只引用本目录内副本。后续版本分支继承这些副本；新增证据保存在所属
版本目录，一份相同内容不必在每个目标目录再次复制。

副本中的原路径仍按原仓库根解释，通过清单映射到本地副本，不能直接当成目标
运行路径。原证据引用的原始归档、durable 状态和日志需按原记录核对；本轮复制
的是可提交的正式记录，不是原始日志的完整闭包。不得把“记录已复制”写成
“所有原始归档已重新核验”。后续实际采用的引用闭包按需补齐，去重归档。

运行日志、PID、缓存、完整 Secret 和认证材料不入 Git。需要的私有原始归档在
所属版本的 `private/` 下受控复制（目录权限 `0700`、文件 `0600`，已忽略提交），
记录其来源、摘要、访问与保留方式；不得
把敏感文件直接当普通 evidence 提交，也不能只保留失效的外部路径冒称归档完成。
发现资料不可访问，先找归档、权限或签署记录，只阻断依赖它的主张，不自动重测。

| 检查层 | 要回答的问题 | 结论边界 |
| --- | --- | --- |
| 复制完整性 | 副本是否等于源文件，来源和原 ID 是否保留 | 可以独立追溯历史记录，不证明目标适用 |
| 原结论身份 | 版本、补丁、输入、场景、durable/marker/清理及原始归档是什么 | 保留原结论；历史开发证据不能伪装客户实装 |
| 目标适用性 | 差异是否改变这一具体断言的成立条件 | 决定复用、补证或重测，不重新签署旧运行 |

原始矩阵可能含历史 pending 或限定范围，按原样保存；用户确认的交付事实、仓库
历史记录与精确客户身份分别记载，不为消除表面差异而改写任一来源。

## 3. 逐主张决定最小补证

每个目标组件先核对准确版本的官方支持/测试范围、升级路径、维护期、配套关系
和发布差异，再映射到项目实际使用的 API、参数、模板、补丁和数据格式。已有
研究按文档标准第 10 节复用并补增量；官方页面缺失先查官方固定版本源码资料，
不把研究缺口直接变成测试任务。

将一个功能拆成它实际承诺的断言。例如“数据库备份恢复语义”“Operator 在新
API 上协调”“卷经节点疏散后仍可读”是不同断言。K8s 变化会触及后两者，不能
无依据地让第一项已经取得的全部深度证据失效。反之，CSI、数据格式或备份链
变化时，也不能把第一项一概标成平台无关。

| 输入变化与官方结论 | 证据处置 | 现场执行的触发条件 |
| --- | --- | --- |
| 只有方案、文档或整仓 SHA 变化，运行输入未变 | 保留旧证据，检查本次文件 | 不触发现场 |
| K8s minor 变化，组件/项目接口不变，官方明确覆盖目标 | 复用原功能深测；核对 API/默认值/条件差异 | 补新的迁移主链，以及尚无适用证据的集成断言 |
| 组件 patch/minor 更新，项目逻辑不变 | 官方配套与增量评估；按断言保留未受影响深测 | 发布差异触达实际路径或出现新的集成证据缺口 |
| 项目模板、编排、权限、补丁、数据格式发生变化 | 精确合同和所属最窄正常/拒绝/恢复验证 | 只扩至已证明受影响的依赖消费者 |
| 官方矩阵未列出或仅有最低版本 | 明记证据力度；查支持政策、迁移文档和源码 | 关键支持未知时阻断该选型；不以全量测试替代官方支持 |
| 独立工具/外部系统不消费变化的依赖 | 归档原证据，记录无影响理由 | 无变化依赖则不启动其独立回归 |

计划动作仍用 `reuse / supplement / rerun / investigate / not-applicable`。
`investigate` 只表示待做影响判断，不表示需要重测；`reuse` 必须绑定副本、适用
断言与未受影响理由；`supplement` 只追加缺失断言；`rerun` 必须指明哪条旧断言
因什么变化失效。`not-applicable` 不得用于删掉仍向客户承诺的路径。

官方兼容矩阵承担其声明的上游兼容前提，不再搭实验复测其全部内部机制。
`tested`、`supported`、`minimum`、接口契约和源码 pin 不可互换；官方支持并不
自动证明本项目编排，但本项目验证也不需要重复上游整套认证。没有变化证据或
明确的新主张缺口，不新增故障、PITR、灾备、性能及长时稳定性回归。复用的性能
数据保留原版本、硬件和负载条件，不改称目标版本实测吞吐或 SLA。

## 4. 目标集成覆盖与现场集合

每跳新增的迁移主链必须经过产品入口 `config.yml + kubecli upgrade`，证明真实
HA 偏差、逐节点 drain/PDB、失败停止/续跑和确认数据保持；目标新建主路径也须
在独立干净边界成立。旧 `--upgrade-only` 的补丁证据不能承担这些新主张。

其余集成按下表组织覆盖，不因存在组件就独立建群、造故障或跑完整业务矩阵：

| 主张归属 | 本次要确认的边界 | 优先取得方式 |
| --- | --- | --- |
| 网络/DNS/Service | API、数据路径、策略和迁移收敛是否受变化影响 | 官方矩阵 + 模板/配置差异 + 已有证据；缺失断言合并进主链探针 |
| 存储/CSI/快照 | 账本、卷身份、调度重挂载、CRD/控制器所有权 | 原深测 + 官方配套；发生变化的挂载/迁移断言最小补证 |
| 中间件/Operator | 实际使用 API、CRD/协调、重连、数据身份、自有补丁 | 原业务/恢复证据 + 官方配套；变化的协调/业务断言集中补证 |
| 安全/入口/观测 | 允许拒绝、实际流量、指标/日志接口 | 复用不变断言；受影响接口加真实业务检查，不凭 Pod Ready |
| 环境/拓扑/架构 | 变化是否依赖运行时、内核、硬件或特定模式 | 原资格 + 官方要求 + 差异判断，只测有变化或新缺口的边界 |

所有继续支持的路径都须有证据去向，但不要求它们全部在本轮现场重跑。等价分析
针对具体断言：两个数据库消费同一 PVC 接口，不证明两种数据库深度行为等价；
同一份迁移中的存储账本可以支持多项共同接口断言。不同 CNI、运行时、Longhorn
V1/V2、RBD/CephFS 也不能仅凭名称相近合并。先检查可复用证据与官方覆盖，再决定
还缺哪些断言，不枚举完整笛卡尔组合，更不默认构建全部组件×全部存储的实验。

组合后的现场步骤必须列出其覆盖的父项/原 ID、具体断言和输入。同一次真实执行
可以支持多个父项；各父项按自己的完整边界验收，不为取得多个 marker 重复执行。
源业务账本在升级前建立，升级后直接读回，不先写入哨兵掩盖数据丢失。关闭、未
安装、已安装的分支先以静态合同或旧证据覆盖，只有相应行为改变才补现场路径。

## 5. 范围与成本约束

P3 冻结两份不同集合：全部承诺的覆盖映射，以及其中需要本轮执行的步骤。
现场集合为“新增主张或已证明失效的断言，扣除适用的旧/官方/静态证据后仍未
覆盖的部分”。K8s 是基座、版本号变化、整仓 fingerprint 变化都不是全量重测理由。

每个现场步骤在启动前必须写明：所属 ID、变化机制或新主张缺口、已尝试复用的
证据、最小反证、共享前置、能同时支持的断言、时间/资源上界、成功/失败/清理
出口。缺口关闭就前进，不继续追加“保险性”资格测试；不另建通用调度框架。

成本记录区分人工/代理工作、无人值守运行和环境占用。模型费用没有真实计量时
标为未知，不能从实验时长换算 token 费用。用户提供的“三天约 700 元”说明不可
承担长期重复回归，不是本项目获得的三天或 700 元预算。具体上限未确定前不得
启动现场；本轮已由 design-only 禁止执行，不因此重复索要日常文档授权。

一次冻结后，每个新增步骤或扩大窗口都须先记录原计划、增加原因、不能复用的
依据、影响 ID 和增量成本。超出已授权范围或预算时停止启动增量步骤，先提交
具体调整；正在进行的安全恢复和清理照常完成。普通范围内步骤不拆成反复确认。
超时或失去可观察进展先定位首个停滞点，不自动全链重跑，也不连续轮询大日志；
runner 提供持久状态和心跳，代理在阶段出口读取必要摘要、异常时再定点诊断。

## 6. 旧门禁与最终验收

现有 broad fingerprint 失效先定位实际变化。纯方案/SHA 变化不得作废全部业务
证据；确属门禁粒度问题时，先补精确因果合同，再修最小 handoff，不删除校验、
篡改旧 hash 或开 WIP 绕过准入。复用原固定模块前检查真实调用计划、参数、隐含
发布/重装/清理范围；不能把 broad runner 包一层新名字就称为独立升级入口。

旧矩阵强制完整项逐一写清适用性：未变能力沿用既有完整验收记录；实际改变的
产品/门禁按所属契约完成受影响模块和最终要求。新增中间件仍执行其完整干净
回归。本次版本维护不默认是重新接入全部中间件。确需修订原强制条款时，列明
原 ID、原范围、变更依赖、替代证据和覆盖证明，按对应范围评审，不能静默跳过。

`UPG-15` 最终 launcher 在任何变更前核验其余适用父项的当前证据，复用证据也须
具备适用性记录。最终计划只包含冻结的迁移主链、目标干净安装及受影响的集成
步骤；历史深测作为前置，不列入本轮实际执行步数。聚焦阶段已完成的独立资格
不再整套塞入最终主链；是否需在主链重验，以它是否依赖主链实际状态为依据。

本轮完整计划实际执行、durable rc=0、零非预期失败、完整成功标志与最终
`LAB_CLEAN_VERIFY_PASS` 均成立才签最终项。父运行真实失败保留，独立子项不能
改签父项；首失败停止依赖链并保存证据，修复仅返回受影响边界。最终要求覆盖
本次交付全部适用项，不是重新执行所有历史验收。

## 7. 可提交证据与交付结论

后续目标证据包含矩阵/子项 ID、适用主张、源/目标身份、配置/制品/官方依据、
差异及复用关系。新增实测另含 run ID、实际命令、原始归档身份与 SHA256、durable
状态、失败数、成功/清理 marker、业务断言和恢复记录。静态或资料证据不伪造现场
run ID。敏感原始资料受控保存，普通摘要不携带可复用认证材料。

该次 GA 就绪意味着目标声明范围的证据闭合；不是旧版本重新 GA，也不是客户
签收。复用结论不冒称本轮重新实测，性能/稳定性不超出已有测量边界。官方、
项目集成、文档验收与客户签收各自表述。关键缺口保持待验收，不以缩短必需窗口
或降低业务断言来压缩成本。
