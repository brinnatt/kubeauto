# 版本选择、分支与支持边界

## 1. 一条 minor 选择一个冻结交付版本

Kubernetes 的 `1.34` 是 minor，`1.34.13` 是其 patch；本目录的“逐版本”指逐
minor 迁移。候选来自 `https://dl.k8s.io/release/stable-1.xx.txt`，总体最新版本
来自 `stable.txt`。锁版时保存官方返回值、观察日期、发布说明及实际下载制品的
SHA256；执行只使用冻结值，不在安装或升级现场查询浮动 stable 并自动切换。

每个目标 minor 在选型截止日选择一个兼容且可交付的最新稳定 patch，不维护该
minor 的所有历史 patch。冻结后出现新 patch 不自动作废已完成证据；评估安全公告、
阻断缺陷和官方前置，有必要时产生明确修订及最小补测，不持续追新导致永远无法交付。
严重安全问题、制品撤回和升级必需修复是修订例外，不能以“一 minor 一版本”拒绝处理。

`stable` 表示可下载稳定发布，不表示仍在维护期。官方当前维护最近三个 minor；
本次已知 1.33、1.34 已 EOL，1.35–1.37 在维护窗口内。第一跳 1.34.13 是迁移
桥梁；现有客户分支的保留不能表述为上游继续提供安全维护。新长期落点必须核对
届时维护窗口和全部关键组件支持，不因 K8s 最新就默认生态已覆盖。

官方建议源 minor 先更新到最新 patch，但它不等于所有路径都强制先补 patch。
`1.33.6 → 1.33.13 → 1.34.13` 与直接第一跳的选择须检查具体发布说明、安全修复、
组件支持和失败恢复；确需源 patch 桥接时记录其必要性、制品和最小验证，不隐式
增加长期维护分支。源、桥接和目标都不能跳过各自组件的官方强制升级前置。

## 2. 选择兼容组合，而非分别选择最高版本

一次选型同时求解以下约束，任一关键约束未知都不能冻结：

| 约束 | 必须记录的依据 | 不成立时的出口 |
| --- | --- | --- |
| 目标运行支持 | 官方支持范围/已测试矩阵及版本 | 换到官方覆盖的稳定组合或保留缺口 |
| 当前至目标迁移 | 官方允许源、桥接版本、顺序及限制 | 增加有依据的中间迁移步骤 |
| 过渡期支持 | 源 K8s、目标 K8s 与混合阶段可用的组件组合 | 提前更新、延后更新或使用官方桥接组合 |
| 配套关系 | Operator、Chart、CRD、引擎、工具、sidecar | 保持官方组合，不能各自追新 |
| 主机与架构 | OS、内核、cgroup、指令集、ABI、AMD64/ARM64 | 验证最小环境变化及其依赖 |
| 项目集成 | 参数、模板、API、默认值、数据格式和自有补丁 | 定点源码核实并做最小产品修复 |
| 生命周期 | 维护期、安全、许可、项目退役及制品可用性 | 独立替换决策或明确受限交付边界 |

已有组件仍满足全部约束时优先复用。选择的是满足组合约束的最新稳定版本，不是
突破官方配套关系的最高 tag。安全或维护期要求变化时，即使版本“还能运行”也需
独立决策。K8s 升级不默认授权数据库引擎大版本升级、CNI 更换或存储引擎迁移。

官方证据的力度分开记录：`tested` 表示列入官方测试，`supported` 表示官方声明
支持，`minimum` 只给下限，`api-contract` 只说明接口关系，`source-pin` 只是
源码采用版本。Chart 的 `kubeVersion` 或 Kubernetes 源码依赖 pin 不是全生态认证。
未提供矩阵时如实保留依据类型及缺口，不编造；缺少关键支持依据阻断对应组合。

例如 Metrics Server 0.8.x 的 1.31+ 是支持范围；Cilium 1.19.5 的 1.32–1.35 是
列出的测试范围；Ceph CSI 的测试范围、CPU 架构和支持窗口需要分别核对。具体
已读事实及边界见 [official-sources.yaml](official-sources.yaml)，不能从本节示例
直接冻结目标。未采用路径也须盘点并决定其支持边界，不能通过不测试而悄悄删功能。

## 3. 最终组合与迁移边分开记录

新建集群的版本组合、在役集群的升级路线和失败恢复路线是三个不同主张。
目标组件可能不支持源 K8s，旧组件又可能不支持目标；必须找到覆盖两个端点或
官方允许过渡阶段的组合。最终矩阵全绿不能代替过渡阶段的兼容证明。

每条迁移边都记录源/目标、前置健康、先后关系、不可逆点、数据/资源身份、停止
条件及恢复出口。etcd、运行时、网络、存储与数据库各自遵守官方升级政策；不能
因为 Kubernetes 不跳 minor 就假设其它组件允许直接跳版本。禁止自动把 CNI 数据
存储从本项目 Calico etcdv3 切成 KDD，或把既有存储卷迁移到新引擎来迎合示例。

## 4. 分支与不可变交付身份

1. 先关联客户实际 release/tag、源码 SHA、制品 digest、配置/拓扑和原证据；当前
   开发快照只用于盘点。历史资料缺口保持可见，不修改日志来补签。
2. 第一条目标分支名为 `v1.34.13`，从已确认源基线创建。后续逐条从上一条已接受
   交付建立；补丁桥接不自动产生长期维护分支。分支创建属于后续实现阶段。
3. 分支表达 K8s 基线，产品 release tag 表达同一基线上的交付修订。二者在
   `release.yaml` 一一绑定；正式 tag 不覆盖，双端架构 digest 和构建来源可追溯。
4. 六仓是兼容审计单元，不是每次必须修改或重建的单元。主仓记录五仓确切提交与
   实际消费制品；未变制品核验复用，各制品仓不强制建立无意义的同名分支。
5. 六仓合同依赖相邻 checkout。多版本并行维护使用匹配的 checkout/worktree
   组合；不让旧分支读取兄弟仓最新 dev 后误报兼容或失败。
6. 公共修复选择性回移，评估在每条受影响分支的依赖。不整条合并新版组件 pin，
   各分支可继承同一份历史证据副本，但须有本目标的适用性结论，不将原 PASS
   改签成另一组合的实测；不同分支不覆盖同一正式镜像 tag。

## 5. 制品与发布范围

对生产、升级、恢复、备份、性能和测试基础设施分别列出消费集合。核验精确
版本、目录映射、输入/build-policy fingerprint、目标架构、历史发布记录及双端
manifest/digest 后，分成可复用、新增、变化和已证明缺失/失效四类；后三类才是
允许构建候选。网络或认证失败属于待读取原因，不能据此默认重建。

发布前给出仓库、分支、SHA、实际 mode、镜像列表/数量和必要性，证明实际集合
包含于允许集合。ext-images 使用既有 changed/selected 能力；k8s-bin 当前会构建
多个历史版本，需要先具备可证明的精确选版能力。ext-bin 只有其内容或契约确实
变化才重建，sp1 无变化就复用。产品镜像与 release workflow 的触发、构建 tools
副作用也要检查，不能推 tag 后才发现范围扩大。

AMD64/ARM64 与 TalkEdu/Docker Hub 证据逐项绑定；临时加速器不固化。官方下载
必须校验并原子落盘。正式构建不能以“已成功下载”替代校验；本次源码盘点发现的
未满足条件登记为后续缺口，不在方案阶段修复。

旧升级门禁使用的 `v1.33.5` 等固定夹具与已交付 tag 保留原身份；不能为了缩小
新分支构建列表而删除旧分支需要的制品或把新版本重标成旧版本。通过精确选择
本次需要发布的版本控制成本，不靠修改历史夹具制造一致。
