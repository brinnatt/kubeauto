# 从基线确认到第一跳交付

本流程用于维护人员按顺序执行。当前只完成方案文件准备与只读源码盘点；阶段
出口是未来必须证明的条件，不是已执行记录。目标目录中的 `gaps` 和正式矩阵
保留真实未完成状态。每一阶段可独立完成的工作继续推进，依赖未满足的动作停步。

## 1. 顺序、输入与出口

| 阶段 | 输入与动作 | 完成条件 | 未满足时停止在哪 |
| --- | --- | --- | --- |
| P0 基线 | 接受已确认全功能 GA；关联客户 release/配置/制品，复制正式证据并核对摘要 | 源身份、副本及缺口可追溯；不重开旧 GA | 只阻断依赖缺失身份的目标结论 |
| P1 官方研究 | 组件清单、四类资料目录、版本差异、安全/弃用/退役、源码歧义 | 关键官方约束闭合，未读/不可访问如实记录 | 不冻结依赖该缺口的组合 |
| P2 组合与路径 | 安装组合、桥接组合、迁移边、环境约束与补丁账 | 每个组件有保持/更新/桥接/替换/不适用的依据；恢复可闭合 | 不修改 pin、不构建 |
| P3 范围冻结 | 精确文件、制品允许集、依赖影响、矩阵 ID、证据复用 | 实现/发布/补测集合与最终计划可审阅，命令/预算/清理明确 | 不触发 broad workflow 或现场 |
| P4 实现与本地合同 | 按已授权范围最小修改生产代码和升级专用自动化 | 所有变更通过相应最便宜合同，真实调用与拒绝顺序成立 | 不运行受影响现场分支 |
| P5 制品准入 | 复用核验、必要发布与双端双架构校验 | 全部实际消费制品可用且身份准确 | 不在现场临时找镜像或换 tag |
| P6 聚焦验证 | runner 租约、干净边界、产品入口和最小反证 | 受影响模块业务、拒绝、恢复和限定清理通过 | 只修复已证明层，不重启无关链 |
| P7 最终验收 | 除最终项外全部适用前置、冻结最终计划 | 一次本次范围的干净完整运行、durable 0、零失败、末尾清理 | 首失败停止依赖路径，保留真实结果 |
| P8 交付 | 冻结源码/制品、有效证据、客户操作与限制 | GA 就绪证据、文档结果和客户签收各自明确 | 不由作者代替客户签收 |

P4 的本地检查先于任何相关远程变更。P4/P5 的源码发布可能有自动构建副作用，
触发前必须完成实际计划核对；不能用阶段名称规避发布准入。当前授权没有进入 P4。

## 2. P0：建立真实源基线

从 `v1.33.6/release.yaml` 的只读六仓快照开始，关联客户交付 tag/提交、产品
二进制 SHA256、六仓实际制品、目标架构、部署配置、拓扑与已启用功能。对照
`inventory.yaml` 的源码版本与客户实际版本，差异逐项记录。交付负责人已确认
全部既有功能 GA，不重新要求整仓验收；配置是否启用只用于建立实际迁移场景，
不能把未启用的已交付能力改写成未 GA。

核查旧 evidence 指向的原始日志/归档、durable rc、marker、清理、版本和配置。
旧数据不可访问时先定位已有路径、归档和权限，不把整个项目重跑当作默认补救。
当前源码快照不绑定客户旧 tag；不能在记录中填“已确认”后跳过此步骤。
正式证据实际复制到源版 `evidence/`，维护 `evidence-manifest.yaml` 的来源、原 ID、
字节数和 SHA256。只读清单中本次涉及的记录；不要每轮递归通读全部历史 JSON、
日志或冻结输入清单。逐主张采用时再补核所需原始归档，不重复搬运相同内容。

## 3. P1/P2：研究与选择

在目标 `research.yaml` 的同一记录上维护每组件官方四类资料入口及完整目录。
已有完整研究基线可按文档标准第 10 节复用并补增量；没有目录记录则补齐，不虚构
已通读。依赖按实际接口边界研究，不递归阅读厂商所有产品。相同上游机制只读一次，
多个组件/任务引用同一结论；稳定结论不为凑证据再搭实验。

逐组件核对发布说明、兼容窗口、API/flags/默认值、CRD 存储与转换 webhook、
准入、运行时 CRI/cgroup、OS/内核、etcd、CNI、CSI/快照、Chart/appVersion、SDK、
数据格式、备份恢复、许可证和已知问题。既有 `-kubeauto.N` 镜像必须核查补丁：
上游是否已包含修复、是否有等价实现、重基后的功能/安全行为是否保持。

组件决策同时回答“新建安装用什么”和“旧集群如何走过去”。不满足两端支持时
设计桥接；无法找到有依据的安全路径时阻断对应组合。目标默认保留原支持功能，
删除或替换已有能力属于明确产品决策，不能在验收计划中自行排除。

## 4. P3：冻结最小范围

在 `release.yaml` 填入精确版本、官方结论、迁移边及恢复条件，在
`acceptance-plan.yaml` 逐项绑定依赖、原矩阵 ID、复用证据和最小补测。
用依赖闭包决定影响，不能只按文件路径：修改一个公共常量可能影响多个功能；
Kubernetes 版本变更也是运行输入变化，即使生产代码没有变化。

资源计划只引用根 AGENTS 的白名单，写入实际主机、角色、租约、容量、端口/
磁盘 allowlist、冲突和清理边界；不复制另一份可能过期的主机权威。无租约不借用
现成集群。独立可运行分支在容量和所有权允许时并行，不能并行改变同一共享状态。

所有新命令在实现前保持 `null`。P3 可冻结行为设计，P4 之后还必须补齐精确入口、
marker、超时和合同结果才能启动；设计通过不是运行准入。成本估算使用已有同类
模块时长、计划关键路径和容量，明确不确定性，不承诺没有依据的压缩比例或天数。

覆盖清单与现场执行清单分别冻结。先给每个断言分配官方依据、归档副本、静态
合同或新增实测；仍有缺口才增加现场步骤。同一主链的真实探针可支持多个父项。
新增步骤必须说明不能复用的理由、最小反证及时间/资源上界，具体要求见
[验收规则第 5 节](acceptance.md#5-范围与成本约束)。不把用户的费用举例当预算，
不把官方资料缺口改成测试任务，不将旧组件最终完整回归默认加入本次最终主链。

## 5. P4：升级编排应证明的生产行为

以下是行为要求，不是可直接执行的 runbook，也不保证现有 playbook 已满足。
实现仍使用 config + kubecli，不能另写 SSH 升级脚本替代产品路径。

| 顺序 | 正常条件及动作 | 停止与恢复边界 |
| --- | --- | --- |
| 预检 | 核实实际版本、集群身份、组合、健康、备份与容量；拒绝跳 minor、降级、错误/浮动制品 | 任何前置失败不改集群；保存原因与读取结果 |
| 组件前置 | 依官方迁移边更新必须提前的运行时/CNI/控制器等；确认源集群仍健康 | 保留原业务账本，按组件自身允许路径恢复 |
| API Server | 依次更新各 API Server，逐个核验 readyz、LB 端点和 quorum 相关健康 | 任何实例失败停止；不继续更新所有节点来“收敛” |
| 控制组件 | 其可访问 API Server 全部满足官方偏差约束后，再更新 scheduler/controller-manager | 按实际 kubeconfig 路由判断，不能只看同机 API 版本 |
| 节点 | 逐节点或经批准批次 cordon/drain，尊重 PDB/卷/本地数据约束，更新 kubelet/proxy，验证后恢复调度 | 不强删受保护 Pod、不默认丢弃 emptyDir 或放宽 PDB；失败不扩批 |
| 组件后置 | 依已评审路径完成必须延后的组件/CRD更新与协调 | 共享控制器、数据格式不可逆点单独确认 |
| 终检 | 实际二进制/节点/镜像版本、跨节点数据路径、身份保持、业务账本与幂等 | 版本一致和 Pod Ready 不能代替业务结果 |

API Server 可以逐台升级，不代表同一台上的 kubelet 可以立即先于其仍可访问的旧
API Server 更新。官方要求 minor kubelet 更新前 drain；当前补丁门禁不能证明
HA 混合版本和逐节点疏散。AIO、HA、Docker/containerd 等继续支持的不同路径在
验收计划中有明确归属；不承诺 AIO 升级零中断。

## 6. 失败、续跑与恢复

在升级 journal 中绑定 run/change ID、集群 UID、源/目标版本、计划摘要、资源
身份、已完成步骤及实际版本。每次续跑先验证所有权、输入、健康、账本和无故障
残留；禁止根据步骤号盲跳、重复不可逆动作或接管外来运行。

失败先保存首命令、durable 状态、渲染输入、事件、Pod/控制器诊断和版本分布。
分类后只修被证明的层，已健康的独立模块可按边界继续。父运行真实失败不能被子
模块 PASS 改写。作用域恢复先去除本轮故障、解锁本轮节点/资源，保留诊断与可恢复数据。

恢复方案分别写清：中断续跑、官方允许的组件撤销、etcd 灾难恢复、业务数据恢复。
备份须包含恢复所需证书/配置/加密密钥的受控保管、版本和完整性；仓库只记身份与
摘要，不保存秘密。etcd 快照不是数据库一致性备份，VM 快照也不自动是安全回退。
恢复整套旧控制面可能丢失恢复点之后的 API 变更，还须处理运行中的工作负载和外部
系统一致性；不能只覆盖二进制或恢复单成员后混入新旧数据集。

每条路径在变更前声明不可逆点、数据损失窗口和业务确认边界；没有经过验证的
恢复步骤不写成可用保障。升级失败不自动授权生产全量 wipe。

## 7. P7/P8：最终范围与交付

最终 launcher 必须在任何变更前核验除最终项外的全部适用前置，拒绝 missing、
pending、fail、过期或未绑定的证据。前置通过后，执行本次冻结范围的一次干净
完整计划；不能从此前聚焦日志拼装成“本轮完整运行”。已确认不变的深度能力
证据作为前置复用，不把最终计划扩成全部中间件的历史 GA 长链。

收证后逐项更新升级矩阵，引用旧组件矩阵证据时保留其真实签署范围。精确标明
源/目标、支持功能与拓扑、制品身份、缺陷关闭、复用/补测边界和清理结果。
正式发布前复核六仓、允许制品集合与产品打包路径，防止漏装目录或意外构建 tools。
客户操作说明在升级目录内闭合；组件已有手册仍为其自身能力权威，需要纠正的
受影响事实才在所属手册最小修改。
