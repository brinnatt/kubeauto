# Kubernetes 与既有组件版本维护入口

适用于 `upgrade/`。先读父目录 [AGENTS.md](../AGENTS.md) 和
[企业文档标准](../docs/documentation-quality-standard.md)，再读本目录
[导航](README.md)、[版本策略](policy.md)、[执行流程](workflow.md)、
[验收与证据规则](acceptance.md) 和 [数据契约](data-contract.md)。
本目录管理跨版本交付，主项目和各中间件仍拥有各自的生产实现与原有验收。

## 当前授权与边界

当前工作是方案落地与只读盘点，不是升级实现或客户变更。不得因为文件存在而
创建版本分支、修改组件 pin、运行升级、构建/推送制品、操作实验室或重签历史证据。
已有授权内的文档修订和本地静态检查自主完成；后续按用户明确的实现范围推进。

所有新增升级专用文件放在 `upgrade/`，包括方案、版本记录、正式升级矩阵、
后续 runner/合同/fixture、升级证据摘要和升级操作文档。根 AGENTS 只保留导航。
现有 `playbooks/93.upgrade.yml`、生产 roles、原 tests/runner、历史证据与组件手册
保持其归属，不迁移、不复制成另一套实现。复用的正式证据及矩阵快照必须按
`acceptance.md` 复制到 `upgrade/`，逐字节校验并保留原签署边界；原文件不改动。
若实现证明生产代码必须改变，在所属
路径做最小修改，并在本目录记录依赖与补测；目录独立不等于绕过产品入口。

## 按序进入工作

1. 确认目标目录与源基线；首次六仓审计遵守父契约。当前开发快照不等于客户交付基线。
2. 读取 `catalog.yaml`、源版本 `release.yaml` 与目标版本 `release.yaml`、
   `acceptance-plan.yaml`、`test-matrix.yaml`，定位尚未关闭的出口。
3. 在目标 `research.yaml` 中维护官方四类资料目录、增量、已知问题与兼容依据；
   `official-sources.yaml` 只是已核实结论和待查入口，不代表研究已完整完成。
4. 先证明版本组合、桥接组合及迁移顺序，再确定代码、制品和矩阵影响。
   不将“最新”“源码注释”“Chart kubeVersion 下限”“曾在旧 K8s 运行”冒充官方完整测试矩阵。
5. 以交付负责人确认的全功能 GA 为源基线，优先复用已有证据。证据副本不是目标
   实测；未知依赖先分析，不整体归零，不重新验收旧 GA，不将复制结果冒签新 PASS。
6. 实现阶段先补最便宜的合同，再运行最窄现场分支；变更范围内的最终干净验收
   仍必须完成。新增中间件、全组件重建和全仓回归不是版本维护的隐含前置。
7. 更新本目录的交付决策与受影响正式记录；GA 就绪、文档检查、方案批准和客户签收分开。

证据按清单与本次主张定点读取，不递归通读归档。支持路径清单用于分配覆盖证据，
不能直接转换成全量现场步骤。每个新增现场步骤须有变化机制或新主张缺口、不可
复用理由及成本上界；未变的历史故障、备份、灾备、性能与长稳不为升级重复执行。

## 拒绝条件

- 目标、源基线、官方关键约束、依赖或恢复出口未知时，不进入相关实现或现场阶段。
- 预发布版、未核验的浮动 tag、不可解释的补丁丢失不能进入冻结组合。
- 发布前实际镜像集合必须包含于已批准集合；不能因旧 workflow 的 broad matrix 而顺带发布。
- 拒绝跨 minor、降级、未 drain 的 kubelet minor 更新、无所有权的资源接管及盲目清理。
- 失败保留首失败和 durable 状态，按产品/门禁/环境/供应链/运行时/Kubernetes 层分类，
  改一个已证明的因果层；拒绝尝试的代码和残留必须回收。

## 状态与检查

升级验收只以目标 `test-matrix.yaml` 为主线，计数与实时汇报沿用父契约。
当前没有升级专用可执行 validator、runner 或 status 命令；任何 `null` 命令都表示
尚不能执行，不得用旧 `--upgrade-only` 或成功标志桩替代跨 minor 证明。
文档阶段只做 [README 的本地检查](README.md#本轮可执行的本地检查)，不汇报产品 PASS。
