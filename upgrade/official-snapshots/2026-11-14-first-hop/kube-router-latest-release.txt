Summary\r\n\r\nv2.12.0 is mostly a reliability release. It changes what kube-router's health check means so that failing syncs no longer get kube-router restarted, adds metrics to cover those failures instead, adds CNI configuration templates, and brings quite a few bug and security fixes to the Network Policy, Network Services, and Network Routes Controllers.\r\n\r\nUser-facing changes:\r\n\r\n* **`/healthz` now only reports liveness** - controllers now heartbeat at the start and end of every sync whether it succeeded or not, so a sync that keeps failing (a rule the kernel rejects, a route that can't be installed, a BGP peer that won't come up) no longer restarts kube-router into a `CrashLoopBackOff`. A failed initial sync in the Network Services Controller is also no longer fatal.\r\n  * If you were counting on restarts to surface sync failures, you'll want to alert on the new `kube_router_controller_sync_last_success` and `kube_router_controller_sync_failures_total` metrics instead. The [health](https://github.com/cloudnativelabs/kube-router/blob/master/docs/health.md) and [metrics](https://github.com/cloudnativelabs/kube-router/blob/master/docs/metrics.md) docs have the reasoning and some example alerts.\r\n* **CNI configuration templates** - the new `KUBE_ROUTER_CNI_CONF_TEMPLATE_FILE` env var has kube-router build its CNI config from a template and write the finished file itself, so the container runtime can't pick up a half-finished config on a freshly booted node (which showed up as transient \"no IP ranges specified\" errors). Also, a `.conflist` CNI config without a `bridge` plugin now fails at startup with a clear error instead of causing a panic later on. See the [user guide](https://github.com/cloudnativelabs/kube-router/blob/master/docs/user-guide.md#cni-configuration-templates) and the [example manifest](https://github.com/cloudnativelabs/kube-router/blob/master/daemonset/generic-kuberouter-cni-conf-template.yaml).\r\n* **BFD improvements** - GoBGP v4.10.0 fixes a bug where a stale BFD administrative reset could kill the next BGP session and leave the peer flapping indefinitely ([#2189](https://github.com/cloudnativelabs/kube-router/issues/2189)), and the new `kube_router_bfd_peer_info` metric exposes the session state of each BFD peer.\r\n* **Network policy fixes**:\r\n  * Egress rules with a named port and no `to` peers used to allow any destination on the resolved port number, and are now limited to pods that actually expose that port. Pods could also end up in the wrong named port entries.\r\n  * Some chain and set names could collide. Because the fix changes chain and set names, expect kube-router to recreate them on the first sync after upgrading (the old ones are cleaned up automatically).\r\n  * Full syncs on the iptables backend are a lot cheaper on nodes with many pods, since kube-router no longer copies and scans the whole filter table once per pod (in our benchmark with 80 pods, a sync went from about 150 ms and 90 MB to about 0.5 ms and 0.2 MB).\r\n* **Service proxy fixes**:\r\n  * Services whose namespace, name, and port name joined into the same key (port `http-alt` on `web` and port `alt` on `web-http`, for example) collided, which left one without a VIP and had the other load balancing to both services' pods.\r\n  * DSR setup now only enters the network namespace of pods in the service's own namespace, where before a selectorless service could point it at pods in other namespaces or at the host itself.\r\n* **Consistent backends for hashing schedulers** - endpoints are now sorted for the `sh`, `dh`, and `mh` schedulers so that the same client reaches the same backend no matter which node it lands on. Existing IPVS services keep their current order, so check out the [troubleshooting doc](https://github.com/cloudnativelabs/kube-router/blob/master/docs/troubleshoot.md#inconsistent-backend-selection-with-hashing-schedulers) if you need to reset them.\r\n* **BGP peer passwords no longer leak into logs** - when the `kube-router.io/peers` annotation failed to parse, the logged error could include the surrounding YAML, base64 encoded passwords and all.\r\n* **Example manifests refreshed** - the daemonsets in `daemonset/` now gate liveness behind a startup probe, use `dnsPolicy: Default` and `cniVersion` 1.0.0, and drop RBAC grants kube-router no longer needs. The proxy-only and firewall-only manifests now use a service account instead of a host kubeconfig and leave the CNI config alone.
