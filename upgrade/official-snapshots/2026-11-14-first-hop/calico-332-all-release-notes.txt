<p>Learn about the new features, bug fixes, and other updates in this release of Calico.</p>
<h2 class="anchor anchorTargetStickyNavbar_DLFK" id=new-features-and-enhancements>New features and enhancements<a href=#new-features-and-enhancements class=hash-link aria-label="Direct link to New features and enhancements" title="Direct link to New features and enhancements" translate=no>​</a></h2>
<h3 class="anchor anchorTargetStickyNavbar_DLFK" id=native-v3-crds-tech-preview>Native v3 CRDs (tech preview)<a href=#native-v3-crds-tech-preview class=hash-link aria-label="Direct link to Native v3 CRDs (tech preview)" title="Direct link to Native v3 CRDs (tech preview)" translate=no>​</a></h3>
<p>Calico now supports installation with native <code>projectcalico.org/v3</code> CRDs as an alternative to the aggregated API server.
The Tigera Operator registers <code>projectcalico.org/v3</code> resources directly as native Kubernetes CRDs — no host-network pods, no ordering dependencies between CRDs and the API server, and <code>kubectl</code> manages v3 resources without an extra install step.
This removes a long-standing source of installation friction on managed Kubernetes platforms like EKS and AKS.
For existing clusters, a new <code>DatastoreMigration</code> controller copies resources from the aggregated API server to native CRDs in place; the datastore is briefly locked but workload connectivity is preserved through the migration window.</p>
<p>Native v3 CRDs require the Kubernetes <code>MutatingAdmissionPolicy</code> feature gate, which is beta and not enabled by default.</p>
<p>Native v3 CRDs are the successor to the aggregated API server, and will become the default install mode in a future release.</p>
<p>For more information, see <a class="" href=/calico/3.32/operations/native-v3-crds>Enable native v3 CRDs</a> and <a class="" href=/calico/3.32/operations/crd-migration>Migrate from API server to native CRDs</a>.</p>
<h3 class="anchor anchorTargetStickyNavbar_DLFK" id=kubernetes-clusternetworkpolicy>Kubernetes ClusterNetworkPolicy<a href=#kubernetes-clusternetworkpolicy class=hash-link aria-label="Direct link to Kubernetes ClusterNetworkPolicy" title="Direct link to Kubernetes ClusterNetworkPolicy" translate=no>​</a></h3>
<p>Calico now implements the upstream Kubernetes SIG-Network <code>ClusterNetworkPolicy</code> resource (<code>policy.networking.k8s.io/v1alpha2</code>), giving cluster admins cluster-scoped <code>Accept</code>/<code>Deny</code>/<code>Pass</code> rules in two well-known tiers — <code>Admin</code> and <code>Baseline</code> — that namespace owners cannot override.
This is how you enforce baseline guardrails and tenant isolation that namespace-scoped <code>NetworkPolicy</code> cannot express.
<code>ClusterNetworkPolicy</code> composes with Calico's existing tiered policy: each upstream tier maps to a new auto-created Calico tier (<code>kube-admin</code> and <code>kube-baseline</code>), and <code>priority</code> maps to <code>order</code>, so you can mix <code>ClusterNetworkPolicy</code>, <code>NetworkPolicy</code>, and <code>GlobalNetworkPolicy</code> resources in either tier.</p>
<p>For more information, see <a class="" href=/calico/3.32/network-policy/policy-tiers/tiered-policy>Get started with policy tiers</a>.</p>
<h3 class="anchor anchorTargetStickyNavbar_DLFK" id=istio-ambient-mode-tech-preview>Istio ambient mode (tech preview)<a href=#istio-ambient-mode-tech-preview class=hash-link aria-label="Direct link to Istio ambient mode (tech preview)" title="Direct link to Istio ambient mode (tech preview)" translate=no>​</a></h3>
<p>Calico now bundles Istio in ambient mode, a sidecarless service-mesh architecture that delivers mTLS encryption and mesh security at much lower resource cost than sidecar mesh.
Existing Calico and Kubernetes network policies continue to work unchanged: Calico includes a modified zTunnel proxy that preserves the original destination port instead of rewriting it to the HBONE tunnel port (15008).
The exception is Istio's Waypoint proxy: if you deploy Waypoint, traffic to it follows upstream Istio behavior and your policies must allow port 15008.</p>
<p>For more information, see <a class="" href=/calico/3.32/operations/istio/about-istio-ambient>Istio Ambient Mode</a>.</p>
<h3 class="anchor anchorTargetStickyNavbar_DLFK" id=live-migration-of-kubevirt-vms-over-bgp>Live migration of KubeVirt VMs over BGP<a href=#live-migration-of-kubevirt-vms-over-bgp class=hash-link aria-label="Direct link to Live migration of KubeVirt VMs over BGP" title="Direct link to Live migration of KubeVirt VMs over BGP" translate=no>​</a></h3>
<p>Calico now provides first-class networking for KubeVirt virtual machines in bridge mode, including live migration of running VMs between nodes without breaking established TCP connections.
A migrating VM keeps its IP and has network policy programmed on the destination node before it goes live there.
Felix re-advertises the VM's route from the new host through BGP as soon as the VM activates, so existing connections survive node maintenance and load rebalancing without reconnect storms.
Live migration requires bridge binding mode and BGP networking (no overlay), and is not supported with WireGuard.</p>
<p>For more information, see <a class="" href=/calico/3.32/networking/kubevirt/kubevirt-networking>KubeVirt networking</a> and <a class="" href=/calico/3.32/networking/kubevirt/live-migration-bgp>BGP routing for KubeVirt live migration</a>.</p>
<h3 class="anchor anchorTargetStickyNavbar_DLFK" id=openstack-live-migration-improvements>OpenStack live migration improvements<a href=#openstack-live-migration-improvements class=hash-link aria-label="Direct link to OpenStack live migration improvements" title="Direct link to OpenStack live migration improvements" translate=no>​</a></h3>
<p>Calico for OpenStack now coordinates live migration with the BGP routing layer so existing TCP connections to a migrating VM survive maintenance, load-rebalancing, and planned-reboot migrations.
On the target compute node, Felix programs the migrating VM's route with elevated priority so the target route wins while both source and target advertise the VM.
Example BIRD configurations for iBGP (using <code>LOCAL_PREF</code>) and eBGP (using BGP communities) show how to propagate that priority correctly between nodes.
Calico also recommends <code>live_migration_wait_for_vif_plug = True</code> in Nova so compute transfer waits until interface, <code>ipset</code>, and <code>iptables</code> programming is in place on the destination.
A new state machine emits INFO-level logs in the Neutron driver and Felix so you can track each phase of a migration.</p>
<p>For more information, see <a class="" href=/calico/3.32/networking/openstack/live-migration>Live migration for OpenStack VMs</a>.</p>
<h3 class="anchor anchorTargetStickyNavbar_DLFK" id=maglev-consistent-hash-service-load-balancing>Maglev consistent-hash service load balancing<a href=#maglev-consistent-hash-service-load-balancing class=hash-link aria-label="Direct link to Maglev consistent-hash service load balancing" title="Direct link to Maglev consistent-hash service load balancing" translate=no>​</a></h3>
<p>The eBPF data plane now supports Maglev consistent-hash load balancing for external traffic to a Service.
When a backend is added or removed, Maglev only remaps a small fraction of flows — long-lived connections survive backend churn, and Calico nodes can act as stable ECMP nexthops for advertised service IPs.
Opt in per-Service with the <code>lb.projectcalico.org/external-traffic-strategy: "maglev"</code> annotation; the feature requires the eBPF data plane in direct server return mode and does not apply to pod-to-Service, NodePort, or Services that set Kubernetes External Traffic Policy.</p>
<p>For more information, see <a class="" href=/calico/3.32/networking/configuring/add-maglev-load-balancing>Add Maglev load balancing to a service</a>.</p>
<h3 class="anchor anchorTargetStickyNavbar_DLFK" id=whisker-policy-filtering-and-ui-improvements-tech-preview>Whisker policy filtering and UI improvements (tech preview)<a href=#whisker-policy-filtering-and-ui-improvements-tech-preview class=hash-link aria-label="Direct link to Whisker policy filtering and UI improvements (tech preview)" title="Direct link to Whisker policy filtering and UI improvements (tech preview)" translate=no>​</a></h3>
<p>The Whisker web console gains additional filtering on the live flow-log stream — including by policy, namespace, pod, and verdict — so you can isolate the traffic you're investigating without leaving the console.
This builds on the flow-logs API (Goldmane) and Whisker components introduced in earlier 3.x releases.</p>
<p>For more information, see <a class="" href=/calico/3.32/observability/view-flow-logs>View flow logs in the Calico Whisker web console</a>.
If you upgraded from 3.29 or earlier, see <a class="" href=/calico/3.32/observability/enable-whisker>Enable the flow logs API and Calico Whisker</a> to turn the components on.</p>
<h3 class="anchor anchorTargetStickyNavbar_DLFK" id=ebpf-tcp-rst-on-backend-pod-failure>eBPF: TCP RST on backend pod failure<a href=#ebpf-tcp-rst-on-backend-pod-failure class=hash-link aria-label="Direct link to eBPF: TCP RST on backend pod failure" title="Direct link to eBPF: TCP RST on backend pod failure" translate=no>​</a></h3>
<p>When a backend pod for a Service goes away, the eBPF data plane now sends a TCP RST to clients with established connections to the failed backend.
Applications fail immediately and reconnect to a healthy backend instead of hanging on a dead flow.</p>

<h4 class="anchor anchorTargetStickyNavbar_DLFK" id=updating-1>Updating<a href=#updating-1 class=hash-link aria-label="Direct link to Updating" title="Direct link to Updating" translate=no>​</a></h4>
<p>To update a previous version of Calico, see <a class="" href=/calico/3.32/operations/upgrading/>our upgrade guides</a>.</p>
<p>If you use Calico Ingress Gateway, this release bumps the bundled Envoy Gateway to v1.8.0, which requires the Gateway API v1.5.1 CRDs. Envoy Gateway v1.8 watches <code>TLSRoute</code>, <code>ListenerSet</code>, and <code>BackendTLSPolicy</code> at <code>gateway.networking.k8s.io/v1</code>. If those CRDs are still served only at an older version, for example <code>v1alpha2</code>, the <code>envoy-gateway</code> pod fails to start with <code>no matches for kind "TLSRoute" in version "gateway.networking.k8s.io/v1"</code>.</p>
<p>If the Tigera Operator manages your Gateway API CRDs (the default), set <code>crdManagement: Reconcile</code> on the <code>GatewayAPI</code> resource so the operator upgrades the CRDs during the upgrade. If a <code>safe-upgrades.gateway.networking.k8s.io</code> ValidatingAdmissionPolicy blocks the upgrade with <code>Installing experimental CRDs on top of standard channel CRDs is prohibited</code>, delete that policy and its binding, then let the operator reconcile. The operator recreates the policy afterward.</p>
<p>If you manage the Gateway API CRDs yourself, install the Gateway API v1.5.1 CRDs before upgrading.</p>

<h4 class="anchor anchorTargetStickyNavbar_DLFK" id=updating-3>Updating<a href=#updating-3 class=hash-link aria-label="Direct link to Updating" title="Direct link to Updating" translate=no>​</a></h4>
<p>To update a previous version of Calico, see <a class="" href=/calico/3.32/operations/upgrading/>our upgrade guides</a>.</p>
<p>If you use Calico Ingress Gateway, this release bumps the bundled Envoy Gateway to v1.9.1, which takes the bundled Gateway API CRDs from v1.5.1 to v1.6.1. Gateway API v1.6 removes <code>sessionPersistence.idleTimeout</code> from <code>HTTPRoute</code>, and Envoy Gateway v1.9 rejects an empty <code>clientIPDetection</code> in <code>ClientTrafficPolicy</code>. A manifest that uses either is rejected once the CRDs are upgraded.</p>
<p>Before you upgrade, remove <code>sessionPersistence.idleTimeout</code> from any <code>HTTPRoute</code>, and any empty <code>clientIPDetection</code> from any <code>ClientTrafficPolicy</code>.</p>
