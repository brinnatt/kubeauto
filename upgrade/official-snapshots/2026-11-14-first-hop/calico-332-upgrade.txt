<h2 class="anchor anchorTargetStickyNavbar_DLFK" id=about-upgrading-calico>About upgrading Calico<a href=#about-upgrading-calico class=hash-link aria-label="Direct link to About upgrading Calico" title="Direct link to About upgrading Calico" translate=no>​</a></h2>
<p>This page describes how to upgrade to v3.32 from Calico v3.15 or later. The
procedure varies by datastore type and install method.</p>
<p>If you are using Calico in etcd mode on a Kubernetes cluster, we recommend upgrading to the Kubernetes API datastore <a class="" href=/calico/3.32/operations/datastore-migration>as discussed here</a>.</p>
<p>If you have installed Calico using the <code>calico.yaml</code> manifest, we recommend upgrading to the Calico operator, <a class="" href=/calico/3.32/operations/operator-migration>as discussed here</a>.</p>
<ul>
<li class="">
<p><a href=#upgrading-an-installation-that-was-installed-using-helm class="">Upgrading an installation that was installed using Helm</a></p>
</li>
<li class="">
<p><a href=#upgrading-an-installation-that-uses-the-operator class="">Upgrading an installation that uses the operator</a></p>
</li>
<li class="">
<p><a href=#upgrading-an-installation-that-uses-manifests-and-the-kubernetes-api-datastore class="">Upgrading an installation that uses manifests and the Kubernetes API datastore</a></p>
</li>
<li class="">
<p><a href=#upgrading-an-installation-that-uses-an-etcd-datastore class="">Upgrading an installation that connects directly to an etcd datastore</a></p>
</li>
</ul>
<div class="theme-admonition theme-admonition-note admonition_YL73 alert alert--secondary"><div class=admonitionHeading_kh8A><span class=admonitionIcon_nw39><svg viewBox="0 0 14 16"><path fill-rule=evenodd d="M6.3 5.69a.942.942 0 0 1-.28-.7c0-.28.09-.52.28-.7.19-.18.42-.28.7-.28.28 0 .52.09.7.28.18.19.28.42.28.7 0 .28-.09.52-.28.7a1 1 0 0 1-.7.3c-.28 0-.52-.11-.7-.3zM8 7.99c-.02-.25-.11-.48-.31-.69-.2-.19-.42-.3-.69-.31H6c-.27.02-.48.13-.69.31-.2.2-.3.44-.31.69h1v3c.02.27.11.5.31.69.2.2.42.31.69.31h1c.27 0 .48-.11.69-.31.2-.19.3-.42.31-.69H8V7.98v.01zM7 2.3c-3.14 0-5.7 2.54-5.7 5.68 0 3.14 2.56 5.7 5.7 5.7s5.7-2.55 5.7-5.7c0-3.15-2.56-5.69-5.7-5.69v.01zM7 .98c3.86 0 7 3.14 7 7s-3.14 7-7 7-7-3.12-7-7 3.14-7 7-7z"/></svg></span>note</div><div class=admonitionContent_LGn1><p>Do not use older versions of <code>calicoctl</code> after the upgrade.
This may result in unexpected behavior and data.</div></div>
<h2 class="anchor anchorTargetStickyNavbar_DLFK" id=upgrade-ownerreferences>Upgrade OwnerReferences<a href=#upgrade-ownerreferences class=hash-link aria-label="Direct link to Upgrade OwnerReferences" title="Direct link to Upgrade OwnerReferences" translate=no>​</a></h2>
<p>If you do not use OwnerReferences on resources in the projectcalico.org/v3 API group, you can skip this section.</p>
<p>Starting in Calico v3.28, a change in the way UIDs are generated for projectcalico.org/v3 resources requires that you update any OwnerReferences
that refer to projectcalico.org/v3 resources as an owner. After upgrade, the UID for all projectcalico.org/v3 resources will be changed, resulting in any
owned resources being garbage collected by Kubernetes.</p>
<ol>
<li class="">Remove any OwnerReferences from resources in your cluster that have <code>apiGroup: projectcalico.org/v3</code>.</li>
<li class="">Perform the upgrade normally.</li>
<li class="">Add new OwnerReferences to your resources referencing the new UID.</li>
</ol>
<h2 class="anchor anchorTargetStickyNavbar_DLFK" id=upgrading-an-installation-that-was-installed-using-helm>Upgrading an installation that was installed using Helm<a href=#upgrading-an-installation-that-was-installed-using-helm class=hash-link aria-label="Direct link to Upgrading an installation that was installed using Helm" title="Direct link to Upgrading an installation that was installed using Helm" translate=no>​</a></h2>
<p>The <code>tigera-operator</code> chart does not contain the Calico CRDs, since Helm does not upgrade CRDs on <code>helm upgrade</code>. There are two ways to get the v3.32 CRDs into your cluster:</p>
<ul>
<li class=""><strong>Apply the CRDs yourself before running <code>helm upgrade</code>.</strong> This is the recommended option. The new CRDs are in place before the new operator starts, so you can configure any new fields ahead of the upgrade, and the CRDs are managed by whatever tooling you already use for the rest of your manifests.</li>
<li class=""><strong>Let the operator apply them.</strong> With <code>manageCRDs: true</code> in your <code>values.yaml</code> (the default), the operator applies the CRDs itself when the new pod starts. You do not need a separate step, but the new CRDs only exist once the new operator is running, so new configuration cannot be applied until after the upgrade.</li>
</ul>
<p>To apply the CRDs yourself:</p>
<ol>
<li class="">
<p>Apply the v3.32 CRDs:</p>
<div data-codeblock-validation=true><div class="language-bash codeBlockContainer__Nwi theme-code-block" style=--prism-color:#393A34;--prism-background-color:#f6f8fa><div class=codeBlockContent_ZApd><pre tabindex=0 class="prism-code language-bash codeBlock_Tso8 thin-scrollbar" style=color:#393A34;background-color:#f6f8fa><code class=codeBlockLines_vJ6I><div class=token-line style=color:#393A34><span class="token plain">kubectl apply --server-side --force-conflicts -f https://raw.githubusercontent.com/projectcalico/calico/v3.32.3/manifests/v1_crd_projectcalico_org.yaml</span><br/></div></code></pre></div></div></div>
<p>Or, using the CRD chart:</p>
<div data-codeblock-validation=true><div class="language-bash codeBlockContainer__Nwi theme-code-block" style=--prism-color:#393A34;--prism-background-color:#f6f8fa><div class=codeBlockContent_ZApd><pre tabindex=0 class="prism-code language-bash codeBlock_Tso8 thin-scrollbar" style=color:#393A34;background-color:#f6f8fa><code class=codeBlockLines_vJ6I><div class=token-line style=color:#393A34><span class="token plain">helm template calico-crds projectcalico/crd.projectcalico.org.v1 --version v3.32.3 | kubectl apply --server-side --force-conflicts -f -</span><br/></div></code></pre></div></div></div>
</li>
<li class="">
<p>Run the Helm upgrade:</p>
<div data-codeblock-validation=true><div class="language-bash codeBlockContainer__Nwi theme-code-block" style=--prism-color:#393A34;--prism-background-color:#f6f8fa><div class=codeBlockContent_ZApd><pre tabindex=0 class="prism-code language-bash codeBlock_Tso8 thin-scrollbar" style=color:#393A34;background-color:#f6f8fa><code class=codeBlockLines_vJ6I><div class=token-line style=color:#393A34><span class="token plain">helm upgrade calico projectcalico/tigera-operator</span><br/></div></code></pre></div></div></div>
</li>
</ol>
<h2 class="anchor anchorTargetStickyNavbar_DLFK" id=upgrading-an-installation-that-uses-the-operator>Upgrading an installation that uses the operator<a href=#upgrading-an-installation-that-uses-the-operator class=hash-link aria-label="Direct link to Upgrading an installation that uses the operator" title="Direct link to Upgrading an installation that uses the operator" translate=no>​</a></h2>

</li>

</li>
<li class="">

</li>
<li class="">
<p>Congratulations! You have upgraded to Calico v3.32.</p>
</li>
</ol>

<h2 class="anchor anchorTargetStickyNavbar_DLFK" id=upgrading-if-you-have-application-layer-policy-enabled>Upgrading if you have Application Layer Policy enabled<a href=#upgrading-if-you-have-application-layer-policy-enabled class=hash-link aria-label="Direct link to Upgrading if you have Application Layer Policy enabled" title="Direct link to Upgrading if you have Application Layer Policy enabled" translate=no>​</a></h2>
<p>Dikastes is versioned the same as the rest of Calico, but an upgraded <code>calico-node</code> will still be able to work with a downlevel Dikastes
so that you will not lose data plane connectivity during the upgrade. Once <code>calico-node</code> is upgraded, you can begin redeploying your service pods
with the updated version of Dikastes.</p>
<p>If you have <a class="" href=/calico/3.32/network-policy/istio/app-layer-policy>enabled application layer policy</a>,
take the following steps to upgrade the Dikastes sidecars running in your application pods. Skip these steps if you are not using Istio with Calico.</p>
<ol>
<li class="">
<p>Update the Istio sidecar injector template to use the new version of Dikastes. Replace <code>&lt;your Istio version></code> below with
the full version string of your Istio install, for example <code>1.4.2</code>.</p>
<div data-codeblock-validation=true><div class="language-bash codeBlockContainer__Nwi theme-code-block" style=--prism-color:#393A34;--prism-background-color:#f6f8fa><div class=codeBlockContent_ZApd><pre tabindex=0 class="prism-code language-bash codeBlock_Tso8 thin-scrollbar" style=color:#393A34;background-color:#f6f8fa><code class=codeBlockLines_vJ6I><div class=token-line style=color:#393A34><span class="token plain">kubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.32.3/manifests/alp/istio-inject-configmap-&lt;your Istio version>.yaml</span><br/></div></code></pre></div></div></div>
</li>
<li class="">
<p>Once the new template is in place, newly created pods use the upgraded version of Dikastes. Perform a rolling update of each of your service deployments
to get them on the new version of Dikastes.</p>
</li>
</ol>
