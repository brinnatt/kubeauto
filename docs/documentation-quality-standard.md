# 企业技术文档编写与验收标准

本标准是作者、开发者和评审者使用的内部交付规范，适用于六仓的新增及修订技术文档。客户组件目录仍遵守既有正式文档集合；本标准、阅读记录和评审表不作为额外的客户组件手册。质量目标是让首次接触产品的实施人员能够完成生产任务，让熟练人员能够迅速查到机制、参数和故障处置依据。篇幅、图数、标题齐全、单元测试通过均不能单独证明达到这一目标。

本标准以现有 [Ceph 九模块文档](storage/README.md)为本项目质量标杆，借鉴其沿真实请求解释机制、区分控制面与数据面、说明状态迁移与能力边界、闭合生产变更和恢复流程的写法。学习这些方法，不复制存储术语或强行套用章节；Ceph 的九份文件及既有结构保持原样。

作者从[官方研究](#1-先研究再组织最后写作)开始，完成[读者路径](#2-用读者任务决定层次)和[章节解释](#4-每个章节必须形成解释闭环)，再依照[场景基线](#5-企业场景覆盖基线)、[操作契约](#6-生产操作必须可执行可停止可恢复)、[图形规则](#8-图用于解释关系不用于填充篇幅)编写。评审者直接使用[验收规则](#11-验收分层缺陷逐项关闭)；分配写作任务时使用[指令模板](#12-可复用写作任务指令)。

## 1. 先研究，再组织，最后写作

### 1.1 固定来源：官方用户手册、官方运维手册、官方技术白皮书、官方开发手册

每次引入产品、新技术或中间件，必须以该产品交付版本的**官方用户手册、官方运维手册、官方技术白皮书、官方开发手册**为研究基线，逐份完成阅读、理解和转化。不能由作者先挑几个拟交付功能，再反向把官方阅读范围缩成几个页面；项目暂未封装某项能力，不构成跳过其官方知识的理由。

上游独立出版官方用户手册、官方运维手册、官方技术白皮书、官方开发手册时，逐份核对完整目录；上游将其拆分或合并时，按下表逐项找到等价官方入口并覆盖对应内容。名称或文件数量不同不减免研究，也不虚构不存在的官方手册。

| 官方文档名称 | 必须盘点和消化的内容 | 对本项目的转化目标 |
| --- | --- | --- |
| 官方用户手册 | 产品概念与对象、安装配置、完整功能目录、业务使用、客户端接入、命令/API 参考、使用限制 | 客户理解功能、选择用法，并从本项目入口走到可判断的业务结果 |
| 官方运维手册 | 生产规划与部署、拓扑与容量、配置维护、健康与监控、安全、性能调优、备份恢复、故障诊断、升级迁移和下线 | 每项生产任务具备前置、步骤、等待、判据、失败停止、恢复及复验 |
| 官方技术白皮书 | 官方架构、设计与原理、核心数据结构/算法、请求及状态过程、一致性与可靠性、故障行为、安全模型、性能容量及设计取舍；无独立白皮书时读取这些官方专题 | 用图、实例和因果解释建立核心产品知识体系，再解释项目集成及边界 |
| 官方开发手册 | 官方应用开发指南、协议/API/SDK、错误与并发、幂等和重试、数据模型/模式演进、扩展插件接口及版本兼容；官方提供产品贡献/内部开发指南时，另盘点其维护接口 | 业务开发知识进入用户内容；项目实际使用的接口、扩展与维护契约进入开发手册，不能只写本仓文件清单 |

先固定产品版本、发行版和许可形态，以及本项目选用的部署方式、客户端语言和扩展。补齐该版本发布说明、已知问题、弃用项、安全公告和兼容矩阵。官网只有滚动 `latest` 时，记录访问日期及可取得的官方文档仓 commit/归档，结合固定版本的 API、配置和源码校正；不能把访问日期当作版本兼容证据。

### 1.2 逐项处理目录，不能自行缩减范围

以官方用户手册、官方运维手册、官方技术白皮书、官方开发手册的完整章节目录为基线，展开至可独立判断的功能、机制和生产任务；按目录顺序或依赖顺序读完正文、配置/命令/API 参考及其前置与限制。下列处理方式必须逐项登记，不能用一句“已查相关资料”替代：

| 目录项的实际情况 | 阅读与正文处理规则 |
| --- | --- |
| 本项目已交付，或客户理解、使用和恢复已交付能力所依赖的机制 | 完整消化，映射到正式手册的具体章节、项目入口和验证依据 |
| 同版本、同发行版具备，但本项目尚未封装或未验收 | 阅读其用途、机制、接口和生产约束，在相应章节说明能力及项目边界；不能冒称不适用、悄悄删项或写成已支持的操作路径 |
| 其它版本/发行版、专属托管服务、未采用语言的重复 SDK 示例、未采用的部署后端或上游贡献流程 | 核对目录项内容与官方适用条件后，记录排除理由及依据；共享概念、协议、安全和恢复条件仍须阅读，不能随该分支一起排除 |
| 不可访问、未读、解释不明或与实现不符 | 保留具体缺口与影响；不得填写已消化或删除该项，不得签收依赖它的内容 |

重复主题可合并阅读与结论，但须保留原目录项到同一结论的映射。研究完成条件是官方用户手册、官方运维手册、官方技术白皮书、官方开发手册的目录均已盘点，所有非排除项已消化并有正文归属，排除项有版本/产品依据，没有被标成已完成的缺口。不是要求阅读厂商全部产品网站、博客和所有外链，也不要求为每个未交付功能新增实现或回归。

依赖范围按实际接口确定：Operator/Chart 读取安装、CRD/配置、协调、升级、安全与删除语义；客户端读取选定语言 SDK 及其协议、认证、错误和重试；存储、身份、监控与备份工具读取项目调用的配置/API、兼容条件和失败恢复。依赖本身若成为新增交付产品，须独立按本节研究该依赖产品的官方用户手册、官方运维手册、官方技术白皮书、官方开发手册，不递归审计所有依赖产品。

在该产品已有 evidence、来源覆盖或评审记录中维护以下字段，不新建方案目录、独立研究报告或客户来源索引：

| 记录项 | 必须包含的内容 |
| --- | --- |
| 版本集合 | 核心产品、控制器、Chart、客户端、工具及依赖的准确版本和来源 |
| 官方目录清单 | 明确标注归属官方用户手册、官方运维手册、官方技术白皮书或官方开发手册，记录官方入口及原章节/主题、URL、版本或 commit、访问日期；包括配置/命令/API 参考与版本说明 |
| 阅读与理解 | 已消化/待处理/有依据排除/不可访问；机制、约束、默认值、版本差异及排除依据；疑问及源码核实结果 |
| 项目映射 | 对应配置、实现路径、制品和产品入口；上游支持与项目支持分别标注 |
| 内容覆盖 | 每个非排除目录项的正式文档与章节锚点；常用任务、原理解释、专题或未交付能力边界；重复项的合并去向 |
| 验证与维护 | 对应测试或操作验证记录、适用环境、遗留问题、维护责任与复核触发条件 |

页面不可访问时优先查官方文档仓库、版本归档或官方离线包，记录缺口并继续独立研究。没有依据的问题不得写成事实；影响安全、数据或生产主线的缺口阻断对应章节签收，不能假称已通读全部文档。

文档工作的主要产出是易于理解和使用的正式手册。官方已经清楚说明的机制，准确理解后按客户任务重组、解释并结合项目入口，不再为该结论逐层审计源码或搭建实验。源码核实针对具体歧义、版本差异和项目集成行为；来源记录按主题复用，重复链接不产生新的研究任务或验收项。已有资料和结论在版本及相关实现未变时继续使用，不反复抓取、全文重读或创建重复报告。

## 2. 用读者任务决定层次

每份手册开头说明适用版本、产品范围、读者角色、需要具备的基础知识、完成后能获得的结果，并提供可点击目录和任务索引。术语首次出现时用中文解释实际含义，保留标准英文名，随后用法一致；不以“显然”“很简单”“众所周知”省略推导。

组织三条互相链接的阅读路径，而不是三份重复正文：

| 读者任务 | 推荐路径 | 完成标准 |
| --- | --- | --- |
| 首次部署与使用 | 必要概念 → 规划 → 前置检查 → 一条推荐生产主线 → 客户端真实业务 → 上线验收 | 读者无需猜变量、拼接跨章节命令或借用作者环境 |
| 日常运维与变更 | 任务索引 → 相应 Runbook → 操作及验证 → 故障/恢复分支 | 可从该任务入口进入；明确共享前提并链接准确位置 |
| 原理、选型与疑难诊断 | 架构与机制 → 决策依据 → 参数/API 参考 → 故障证据与限制 | 可解释行为、比较方案、定位参数及风险来源 |

常用能力先于低频能力，推荐路线先于替代路线，正常步骤与异常分支分开。实验演示须明确区别于生产默认；快速开始不得以关闭认证、TLS、持久化或可靠性保护换取成功。长任务按自然阶段拆分，每个阶段保留清晰的输入和出口；不能把整章压成一个不透明脚本。

内容按目的区分概念解释、教程、操作任务、参考信息。它们可在同一正式手册中形成章节，但不能让读者在执行到一半时突然跳进长篇原理，也不能把白皮书写成参数表。交叉引用必须指向具体问题所在章节，并在当前位置保留继续操作所需的最低信息。

### 2.1 消化与取舍：让正文成为本产品的连续知识体系

先在第 1 节的同一记录中把“官方用户手册、官方运维手册、官方技术白皮书、官方开发手册的原目录项 → 消化后的知识 → 客户问题 → 本项目配置/行为及证据 → 正文位置”对齐，再组织正文；不用新建方案或报告。官方主题可以合并，但客户理解、执行和恢复所需的信息必须保留。压缩的是重复、无关分支和低频参考的展开，不是因果、前提或操作出口；不能用过度概括换取短篇幅。

为相互衔接的客户任务选取与交付能力相符的贯穿实例，保持对象名称、身份、输入输出和后续变更一致；独立用途可以另设实例并说明边界，不强行把所有能力塞进同一业务。先建立对象关系，再沿关键操作、状态变化、故障和恢复解释其变化。图中展示的每个关键关系要在文字中说清原因及后果；示例解释输入为何这样选、输出如何形成、改动会产生什么影响。由简单任务逐步引入必要概念，不能在读者尚未理解对象时堆叠缩写，也不能为覆盖主题拼成彼此脱节的百科条目。

每个事实有一个主要归属：白皮书解释机制与决策，用户内容教会业务使用，运维内容闭合生产任务，开发内容说明维护契约。其它位置保留当下必需的结论并精确交叉引用，不复制整段原理、完整测量表或整套命令。已完成回归的事实应重组为客户可用的实例、结果和判断依据；失败重跑时间线、内部进度、过期状态和补丁发现过程不进入客户正文，仍有效的技术限制转写为相应任务的条件或异常分支。

## 3. 正式文档各司其职

| 正式内容类型 | 主体内容 | 与其它手册的边界 |
| --- | --- | --- |
| 用户手册 | 产品理解、部署、业务接入、常用功能、客户端/API 使用、完整业务示例和使用限制 | 解释业务开发者如何使用，而不止于管理员安装成功 |
| 运维手册 | 上线规划、巡检、告警、容量、维护、数据保护、变更、灾备、排障与下线 | 每项任务有生产闭环；参数速查和任务索引便于检索 |
| 技术白皮书 | 架构、请求和控制路径、数据模型、状态机、一致性、可靠性、安全、性能、选型及边界 | 从机制推导取舍；项目补丁等维护细节指向开发手册 |
| 开发手册 | 官方开发资料中本项目采用的协议/API/扩展契约，以及本项目代码边界、配置到资源的映射、幂等、制品、测试、版本维护和发布 | 业务接入实例归用户内容；解释接口选择与维护扩展方法，不将内部回归流水作为客户操作 |

采用 PXC 风格的中间件将用户与运维内容合并为 `operations-manual.md`，另保留独立的 `technical-whitepaper.md` 和 `development-manual.md`。不能因为只有三份文件就压缩项目用户手册、运维手册、技术白皮书、开发手册的内容覆盖。Ceph 保持九模块布局。

### 3.1 技术白皮书必须消化官方技术体系

白皮书以客户理解技术栈、判断架构和解释运行行为为主线。来源及阅读完成条件执行第 1 节官方技术白皮书这一类的完整基线，不能只选与当前补丁有关的几页。不能把 Operator 部署资料当成整个数据库或消息系统的原理资料，也不能只翻译摘要、列功能、拼接链接或摘录源码。

先根据产品实际机制建立知识主线，再解释本项目的集成方式。例如数据库沿数据模型、查询、日志、复制与事务展开；消息系统沿生产、持久化、投递、确认、顺序与重放展开；存储或网络沿 I/O 或连接路径、状态归属、转发与故障隔离展开；控制器沿声明、协调与实际状态展开；SDK、库或命令行工具沿输入、调用、输出、错误及兼容性展开。这些是识别关键路径的示例，不是固定章节，也不推定产品具有集群、持久化或 Operator。各主题需解释参与者和权威状态、关键数据结构或算法、一次操作/故障的完整过程，以及由此产生的取舍；安全、可靠性、容量和生命周期按第 5 节判断适用性。未作为项目接口交付的上游能力须标明边界，不能因未交付而省略理解已交付机制所必需的知识。

每个主要机制主题要形成“客户问题 → 图解或具体实例 → 因果解释 → 适用的真实验证结果 → 决策及边界”。图解负责显露关系，文字解释为何如此，实例和数据帮助读者判断实际行为。简单概念无须硬配图，没有对应实测的主题明确区分官方机制与项目验证范围。项目补丁、测试夹具和维护实现放入开发手册；白皮书只保留理解机制和选型所需的集成差异，避免例外说明挤占正常工作原理。

## 4. 每个章节必须形成解释闭环

先说明读者遇到的问题和本节要得出的结论，再用机制、示例和步骤支撑。需要多少文字由问题复杂度决定；一行概括加名词表不等于讲透，长篇重复也不增加价值。根据章节类型回答下列问题，不要求每节机械复制同一组小标题：

1. **是什么、为何需要：** 与已有概念是什么关系，解决哪个真实任务，何时适用。
2. **如何工作：** 沿一次请求或状态变化说明参与者、权威状态、执行顺序、确认条件以及故障后的行为。
3. **如何选择：** 推荐值/方案的依据是什么；替代路线的适用条件、成本、限制和兼容性是什么。
4. **如何使用：** 给出完整示例或链接到连续操作任务，明确输入和控制入口。
5. **如何判断：** 成功、失败及结果未知各意味着什么；用什么状态、输出和业务证据区分。
6. **如何恢复：** 哪个条件必须停步，如何保留证据、恢复服务、核验数据和收回临时变更。

解释需展示因果。例如讲复制，必须说明写入确认与副本确认、持久化确认的关系，以及网络分区或故障转移时的可见行为。不能从“有副本”直接得出“不丢数据”。结论必须标明成立的前提；项目默认、上游默认、推荐配置、强制限制和实测结果分别注明。

## 5. 企业场景覆盖基线

下表是研究和评审基线，不是给所有产品生搬硬套的章节模板。按客户任务和官方机制判断各能力域的适用性，再展开常见和特殊场景；不适用项在第 1 节的既有覆盖记录中写明理由。区分“不适用”“上游支持但本项目未交付”和“依据或验证不足”，后两者不能为省略内容而登记成不适用。适用的容量、安全、稳定性、性能和易用性要求贯穿主线，不能靠结尾一段概述补齐。

| 能力域 | 企业常用场景 | 需单列的特殊场景与边界 |
| --- | --- | --- |

Redis 的覆盖应由其官方目录展开，至少涉及数据类型和业务模式、过期与淘汰、复制、Sentinel、Cluster、RDB/AOF、ACL/TLS、客户端协议及发现、pipeline、事务、脚本/Functions、发布订阅/Streams、已交付扩展、内存/延迟/基准、升级迁移与诊断。每项应有正文或明确的适用边界；不能只写 Operator 的安装和测试。

覆盖不等于承诺实现所有上游功能。Redis Open Source、Redis Software、Redis Cloud 和云厂商服务的能力须分别核实；许可、商业服务、Active-Active、托管备份等不能未经实现和验证写成本项目能力。

## 6. 生产操作必须可执行、可停止、可恢复

每个操作任务必须交代以下契约。可用简短引言、前置清单和步骤表达；避免在每个短命令前重复一张大表。

| 阶段 | 操作说明必须包含 |
| --- | --- |
| 任务入口 | 目标、适用拓扑/版本、执行人权限、执行主机/容器、工作目录、工具版本和上下文 |
| 前置条件 | 当前健康、容量/故障域预算、依赖、变更窗口、有效备份/恢复点；给出检查方法和准入条件 |
| 输入准备 | 每个变量/文件/凭据的来源、样例、需替换字段、作用域、权限、保存位置与生命周期 |
| 执行 | 按序的产品命令和完整最小配置；每步用途、变更对象、等待条件、超时、重入行为及观测方法 |
| 结果判断 | 期望输出/状态的代表性样例；变化字段、成功阈值与失败条件；控制面、数据面和业务层分别验证 |
| 异常停止 | 首个未满足条件在哪里停；保留哪些证据、避免哪些继续动作，如何限定影响范围 |
| 恢复出口 | 具体回退/恢复步骤、前提、不可逆点、业务与数据复验、临时参数/故障/文件的回收 |

主线必须从公开前提走到客户业务结果。由 kubeauto 管理的部署通过 `config.yml` 与文档规定的 `kubecli` 入口完成；独立工具、SDK 或库使用其正式 CLI/API，遵守所属产品的独立边界。直接 Helm、kubectl、SSH 或原生客户端承担诊断、业务使用或明确授权的原生运维角色，不得悄悄替代已有产品收敛入口。声明式配置与在线命令并存时，必须说明哪一份是权威、临时变更如何写回或恢复，避免下次 reconcile 覆盖。

命令与输出分开使用相应代码块；可执行命令不带提示符。变量在首次使用前定义，后续独立 shell 必须重新建立所需上下文。不能依赖作者的 alias、上一步未保存的环境变量、隐式 kubeconfig、实验室地址、旧资源、测试脚本或隐藏密码。跨文件/客户端示例的对象名、拓扑、认证和协议必须一致。

区分完整可执行实例、需替换输入的模板、解释性片段；模板逐项说明替换方法，解释性片段不得被描述为生产命令。Bash 可执行块禁止裸 `<占位符>` 和未经定义的变量。凭据从受控文件、环境或 Secret 引用进入，不出现在命令参数、仓库、样例输出或诊断包中。

破坏性操作、扩大权限或绕过保护的后果必须在动作之前说明，并给出对象身份核验与安全替代方案。异常、回滚和风险通常置于相应主步骤后的引用分支；强制前置安全条件不得藏在执行后。不得为了显得主线简洁而省略数据损失风险，也不得把无关告警堆满主线。

“等待完成”“检查正常”“必要时恢复”必须具体化为检查命令、预期状态、超时和下一步。异步任务返回 accepted、scheduled、HTTP 2xx 或 Pod Running 只证明局部状态。echo 成功标记仅可汇总已经验证的结果，不能创造验证结果。回退须考虑状态、数据格式、凭据、客户端及资源身份，不能只改回镜像 tag。

## 7. 性能、稳定性与安全需要可判断的依据

性能章节先说明业务负载和瓶颈模型，再给容量估算和测试方法。记录对象大小与分布、读写比例、并发/连接、命令组合、pipeline、TLS、持久化、复制、资源与工具版本；提供测量窗口、预热、延迟 p50/p95/p99、吞吐、错误率、资源峰值及恢复期表现。计算式注明单位、假设和余量，示例值不能变成跨硬件保证。

调优按“现象 → 观测 → 瓶颈假设 → 单项调整 → 同负载复测 → 接受或撤回”组织。每个参数说明作用机制、层级、默认来源、建议范围、代价、是否重启及恢复方法；不得罗列一组“最佳参数”让客户盲目复制。生产压测必须界定业务影响、数据边界、停测条件和清理范围。

稳定性区分可用性、一致性、持久性和可恢复性。说明允许的故障、检测与接管条件、客户端重连、恢复依赖以及可能丢失或不可见的数据；给出 RPO/RTO 的定义、测量方法和成立条件，不以副本数或测试 PASS 保证零丢失、零中断。灾备必须包括恢复验证和回切，备份文件存在不代表可恢复。

监控指标必须解释来源、类型、标签、单位、采样窗口、聚合方式和异常含义；告警给出阈值选择依据、持续时间、严重度、初步诊断与处置链接。缺失样本与指标为零分别处理，不把平均延迟当成尾延迟。安全同时验证允许路径和拒绝路径，给出最小授权和轮换失败后的恢复方法。

### 7.1 将官方与项目验证成果转化为正文

官方 GA 能力说明、官方验证结果、公开生产案例与测量数据，以及本项目验收成果，均可作为正文依据。逐项核对能力成熟度、适用版本和成立条件：GA 产品中的功能仍可能标注 experimental，不能一概视为 GA；官方机制和限制可直接用于解释与设计，官方数据须注明发布者、来源、硬件、拓扑、配置、负载及测量口径，缺失条件如实说明。官方结果不能冒称本项目实测或客户环境保证，本项目实验室结果也不能代替官方支持边界。

写作前先复用适用的官方资料，再从当前矩阵、evidence 及其绑定的原始日志提取项目材料。核对版本、输入、场景、结果、退出状态和日志摘要后，按客户任务选择证据；已有适用证据直接使用，不为获取相同事实重跑现场。内部阅读记录补充“主题/客户问题 → 官方机制与验证来源 → 项目集成差异及验收场景/日志定位 → 可发表的步骤、数据或现象 → 正文章节 → 结论边界”。逐项处理交付能力的证据：用于正文、与同类合并，或说明不适用/资料不足的原因。纯制品校验、清理和静态契约不必都写进客户白皮书。

产品矩阵先对照官方能力、前置条件、推荐操作、失败路径和已知限制，再确定本项目需要证明的集成差异。每个场景写明官方依据、待证明的项目行为及最小反证；稳定的上游机制不因写作或重新说明而重复搭建实验，已有有效项目证据按依赖复用。新增配置、自动化、主机与磁盘操作、故障恢复及本项目性能承诺仍须通过所属产品入口验证；官方 GA 不自动赋予项目矩阵 PASS，也不免除既有强制验收。

正文必须呈现证据支持的具体事实。只有矩阵链接、evidence 文件名、成功标志或“已经 GA”不能代替结果。客户应在本页看到场景条件、关键实践步骤、代表性输出/测量值及其解释；仓库内的来源链接供追溯，离线交付也应保留可识别的版本和场景出处，不能要求客户读取内部日志才能理解结论。

| 证据类型 | 应转化的客户内容 | 必须保留的解释与边界 |
| --- | --- | --- |
| 安装、业务与幂等 | 连续产品步骤、业务输入输出、变更前后对照 | 哪些状态证明可用，哪些身份/配置应保持 |
| 性能与长时负载 | 测试条件表、测量结果表或数据图、关键业务校验 | 数据规模、负载、资源、持续时间、延迟/吞吐口径、错误与重试；不能外推生产上限 |
| 故障与恢复 | 故障时序/状态图、业务现象、恢复后的数据验证 | 注入对象、允许与拒绝路径、确认写入边界；未记录时间不编造接管时间 |
| 备份、PITR 与灾备 | 备份到恢复的实践、时间边界图、恢复前后数据对照 | 版本/拓扑/密钥及恢复链前提；目标时刻前保留、时刻后排除的实际判据 |
| 安全、轮换与所有权 | 允许/拒绝对照、轮换阶段及实际结果 | 新旧身份、权限与信任变化；不泄露凭据或内部环境 |
| 容量、扩缩与告警 | 前后容量/成员/放置表、告警触发与解除过程 | 实际文件系统与数据结果、资源代价及恢复条件 |

提取结果时保留测量口径。业务错误、可恢复重试、最终未完成请求和数据校验失败分别报告；汇总值、单次值、估算值和示意值分别注明。日志未采集的指标标为未测，不从 PASS 倒推数值；不同运行、拓扑或硬件的数据不能拼成同一次测量。所有性能或时效数字必须同时给出足以解释它的条件，不能把实验室读数写成 SLA、生产容量或跨产品优劣结论。

## 8. 图用于解释关系，不用于填充篇幅

当关系、流程、时序或状态用文字难以一眼判断时使用 Mermaid；简单事实用文字即可。先确定图要解答的问题，再选择类型：

| 类型 | 合适用途 | 必须表达的语义 |
| --- | --- | --- |
| `mindmap` | 技术体系、能力域与学习入口 | 分类层级；不能把分类线当成请求或依赖方向 |
| `flowchart` | 架构、控制/数据路径、生产流程与故障诊断 | 节点职责、箭头含义、边界；决策条件、正常/异常出口 |
| `sequenceDiagram` | 一次写入、认证、复制、故障转移或轮换 | 参与者、先后、确认点、超时与失败分支 |
| `stateDiagram-v2` | 成员、迁移、升级、恢复与生命周期 | 状态、触发条件、不可逆转换和恢复路径 |
| 图表/曲线 | 容量、性能、趋势与方案比较 | 单位、负载、来源与适用范围；假设数据明确标为示意 |

图前说明问题，图后解释关键路径、结论及限制。图中的名称、箭头、拓扑和数字与正文、固定版本和实现一致。不能让读者只凭颜色、截图或图形理解关键步骤，必须提供文字解释；宽图拆成总览和局部机制图。检查实际交付平台的 Mermaid 支持并渲染预览，无法渲染的图不得签收。不得设最低图数，也不得用密集图替代推导。

起草前先决定问题的表达方式：组件职责与边界用架构图，请求与确认点用时序图，恢复/升级/PITR 用状态或时间边界图，方案差异和前后结果用表，测量趋势与分布用真实数据图，客户行为用实践步骤及输出。正文围绕图、实例和数据解释因果，删去已被清晰表达的重复叙述，保留理解所需的推导、条件和边界。图或命令块之后仍需解释读者应观察什么、为何得到该结果、如何据此选择或处置；装饰性总览图和大段代码不能代替讲解。

数据图保留原始来源、筛选/聚合和计算口径，生成可独立查看的图形制品并检查坐标、单位、样本和图文一致性。单个数值或少量离散结果用表即可；不从只有汇总分位数的日志捏造延迟分布或时间曲线。机制示意和真实测量清楚分开，不用示意图暗示已实测。

## 9. 参考与速查必须能直接使用

参数参考列出名称、类型、单位、有效范围、默认值来源、项目值、配置位置、作用层级、动态/重启生效、依赖、风险及对应任务。相近参数解释差异与相互约束。客户需调整的参数详述；完整上游参数范围用覆盖映射和准确参考链接承接，不能漏掉影响生产的参数。

故障入口按客户可见现象或告警组织。每个入口给出“现象 → 最小检查 → 证据分叉 → 根因层 → 处置 → 业务/数据复验 → 临时变更回收”。先只读诊断，再实施有依据的变更；日志给出代表性样例及解释，区分产品、配置、环境、制品、运行时、Kubernetes/控制器和客户端问题。普通恢复与专家修复分层，专家动作需明确前提和影响。

术语、任务索引和交叉引用帮助读者定位信息，不替代正文。表格用于对照，连续文字负责解释因果。官方引用紧邻机制结论或融入白皮书/开发手册；客户完成主要任务所需内容必须在本项目文档中闭合，不能让其到多站点自行拼接。

## 10. 写作与维护纪律

用准确、自然、正式的中文，优先主动句和具体动词，术语与命名保持一致。标题说明概念或要完成的任务，避免“其他”“高级功能”等无法检索的容器。每段发展一个观点；避免名词堆积、口号、空泛优点、重复结论、内部开发对话和测试时间线。

首次引入按第 1 节建立官方用户手册、官方运维手册、官方技术白皮书、官方开发手册的完整研究基线；后续新增功能、升级、修复或引入依赖时，在同一记录上增量维护，按以下顺序推进，不重建另一套资料或验收体系：

1. **实现和场景设计前：** 核对目标版本的官方用户手册、官方运维手册、官方技术白皮书、官方开发手册的目录变化，以及发布说明、已知问题、弃用/安全及兼容性变化。新增目录项必须处理；旧来源、结论及项目输入未变的部分直接复用。旧记录没有完整目录映射时，如实补齐缺项，不能假称已有完整基线。
2. **确定实现和验证边界：** 将每个变更主题对应到代码/配置/依赖、所属矩阵 ID、预期正常/拒绝/恢复行为及最小反证。接口前置、默认值、数据格式、所有权、权限、并发、超时/未知结果、升级与删除语义从已消化的官方资料和固定实现取得，不从示例猜测；官方不明确或与集成行为不符时定点查源码。没有依据的关键假设不得直接进入有状态现场回归。
3. **回归结束后：** 按第 7.1 节把已验证的项目行为、原始输出与测量、故障和恢复结果写回对应章节，更新支持边界、来源及证据绑定；未验收功能仍明确标为未交付。项目用户手册、运维手册、技术白皮书、开发手册中涉及同一事实时，只修改其主要归属和引用，不批量改动无关手册。

本节规定资料、实现、验证与正文的衔接；产品是否可启动、回归范围、证据失效与最终 GA 仍执行主仓和所属矩阵的既有契约。仅修订文档不据此启动产品开发或重复回归。

文档缺陷只修对应事实或任务。对 Ceph 和其它成熟功能，阅读标杆不构成修改授权。禁止为了符合模板重排全部文档，也禁止在文档任务中顺带重构产品代码。

## 11. 验收分层，缺陷逐项关闭

| 层次 | 检查方式 | 能证明什么 |
| --- | --- | --- |
| 来源与覆盖 | 按第 1 节分别核对官方用户手册、官方运维手册、官方技术白皮书、官方开发手册的完整目录及每项阅读/排除结论、正文去向；再反查客户任务的知识、入口和结果依据 | 可定位漏读、无依据排除和正文遗漏，不能用几个来源链接或笼统“全部覆盖”替代 |
| 内容评审 | 沿读者任务检查机制、决策、示例、限制与检索路径 | 信息能解释问题并支持客户决策；不是简单功能罗列 |
| 静态检查 | 链接/锚点、Markdown、代码语法、配置/模板、字段/版本契约、图形渲染 | 可机械验证的正确性；不能证明文字深度或操作成功 |
| 操作验证 | 将文档步骤与现有产品验收证据对应；新增或改变执行行为时补最小验证 | 有证据支持该任务的具体版本、前提和结果；复用与新增实测范围分别说明 |
| 读者路径检查 | 按新手主线与熟练人员检索路径检查输入、上下文、步骤衔接和判断依据 | 读者无需猜测或作者口头补充；默认是文档检查，不操作现场 |

不能以关键词命中、字数、图数、标题数量或章节存在作为内容质量 PASS。评审记录采用“要求 → 具体章节/任务 → 依据/验证 → 缺陷 → 修复与复核”的形式；自评不冒充客户签收，也不虚构读者参与。默认由作者检查两类读者路径，发现具体缺陷后修正对应章节；只有本次任务明确要求时才安排非作者或客户参与，并按约定范围记录结果。检查次数取决于实际缺陷，不以反复换代理、重复审计或对整篇文档重新签名作为质量要求。

评审记录至少包含下面这些字段；把实际章节和证据填入，不把模板行当成已完成记录：

| 要求/官方主题 | 文档与章节锚点 | 版本依据/验证记录 | 检查结果与具体缺陷 | 修复位置与复核结果 |
| --- | --- | --- | --- | --- |
| 明确的主题或客户任务 | 可直接定位的正文 | 来源版本、操作条件和结果 | 已满足/待完成/不适用及理由 | 修改内容、复核人/方式及仍未关闭项 |

以下问题必须阻断文档签收：官方用户手册、官方运维手册、官方技术白皮书、官方开发手册中任一来源目录缺失、目录项未处理或排除无依据；错误的版本/机制/能力承诺；生产主线缺少必要输入或验证；示例不可执行或误用入口；未说明的数据损失/越权/不可逆风险；回退或恢复无法闭合；关键图文矛盾；关键链接失效；把未验证任务写成成功保证。措辞、排版和索引缺陷也要逐项关闭，不得用总分抵消阻断缺陷。

内容评审还必须在实际章节上回答：读者能否沿图或实例复述关键机制；能否凭正文中的步骤、输出和数据判断结果；能否说明测量条件及不可外推的结论；能否由机制和结果作出方案选择。检查记录指出具体章节、已解释的因果、示例输入输出和仍缺的环节，不能只填“已覆盖/pass”。首次实施者应能连续走到业务结果；熟练运维应能从任务入口独立找齐前提、停止和恢复；业务示例与白皮书的同名对象须能相互对应。已有对应验收成果却只写抽象要求、只链接 evidence 而不解释结果、缺失核心技术体系、用大段重复文字掩盖关系，均属内容缺陷，关闭前不得签收相关章节。不能以“已挂接全部证据”或“新增多张图”代替这项检查。

所有适用覆盖项、操作契约和评审缺陷逐项完成，才可称文档满足本标准。产品 GA 回归、文档语法检查和文档质量签收是不同证据，不互相替代；旧版本 PASS 不自动证明新标准下的文档合格。“能够成功执行”以版本、前提、具体任务和相符的验证证据为依据，不作无条件成功保证。

文档涉及新的生产动作或改变现有操作行为时，遵守所属产品的固定 runner、最窄聚焦验证及清理阶梯。既有产品路径已有适用的有效证据，且入口、参数语义和前置条件一致时，复用该证据并核对文档；正文对象名替换、示意容量缩放或步骤拆分不自动要求逐字重跑。涉及权限、数据安全、容量成立条件或执行顺序的实质变化，仍须分析影响并验证。

纯文档工作默认执行“理解官方资料 → 结合项目整理正文 → 一次完整的内容及读者路径检查 → 必要静态检查 → 修正具体问题”。它不默认授权开发测试 runner/helper、增加验证镜像、搭建集群、故障注入或重跑整套 GA。已有产品门禁确有具体覆盖缺口时，先说明缺口与本次交付的关系，优先复用固定入口补最小场景；不得以文档完整性为由另建测试工程。新增中间件的产品实现和 GA 验收仍遵守原产品测试契约，文档编写不重复这套验收。仅修改标准、索引或不影响行为的解释文字时，不启动实验室回归。

## 12. 可复用写作任务指令

以下模板用于内部写作任务，先填清范围再使用；它不应出现在客户组件手册中。

```text
任务：为【产品/能力】编写或修订【正式手册及章节】。
版本与边界：【固定版本、项目入口、拓扑、能力与明确排除项】。
读者与结果：【角色、基础知识、需要理解/完成/判断/恢复的客户任务】。

执行本标准及适用 AGENTS.md、矩阵和运行手册，以 Ceph 标杆学习解释方法。
修订时先定位现有正文的具体缺陷；新编时先组织客户任务与必要知识，不虚构旧稿评审。
遵守所属产品的正式文档集合与功能边界，修改内容放在其主要归属。
按第 1 节分别盘点交付版本的官方用户手册、官方运维手册、官方技术白皮书、官方开发手册的完整目录，
逐项消化、映射或有依据排除，不能自行挑几页替代。
官方入口名称或文件拆分方式不同，按第 1 节找到对应内容；未封装能力仍说明知识与项目边界。
首次引入建完整基线，后续变更按第 10 节复用未变结论并补齐增量；源码只查具体歧义。
项目用户手册、运维手册、技术白皮书、开发手册按第 3 节分工，保持既定文件布局。

按第 2.1 节消化重组：官方知识 → 客户问题 → 图文解释与实例 → 项目行为及证据。
按第 3.1、5 节确定本技术栈的机制主线与适用场景，再解释实际集成及依赖边界。
把官方概念、步骤和参考组织成推荐主线、常用任务、进阶专题及速查；合并重复，
保留理解和安全操作所需的信息。让客户沿请求和状态变化理解原因，并能判断取舍。
用准确图解显露关系，用文字解释因果，用例子和真实数据说明行为及其成立条件；
不以摘要、术语、图数或长篇幅代替解释。图须实际渲染并核对。

按第 7.1 节读取适用矩阵、evidence 和绑定原始日志，把真实实践及测量写进正文。
注明版本、条件、统计口径和外推边界；官方能力、项目实现、实测与示意分别表达。
不为取材重跑有效回归；内部失败重跑过程不进入客户正文，技术限制放入对应任务。
操作遵守第 6 节：输入来源、角色/位置/上下文、前置、产品入口、等待、结果、
失败停止与恢复连续闭合。同名对象和后续迁移/备份必须衔接，不让客户自行拼步骤。

按第 11 节完成一次完整的来源、内容和两类读者路径检查及必要静态检查，修具体缺陷。
检查记录定位正文中的因果、实例、输入输出及剩余缺口，不只登记“覆盖/pass”。
复用有效操作证据，只有实质改变操作行为才补最小验证；不默认增加代理、门禁工程、
镜像、集群或产品全量回归。产品 GA、作者文档检查与客户签收分别表述。
只汇报实际完成范围；未读、不可访问、未验证及未关闭问题如实保留，不冒领历史验收。

```
